# برنامهٔ تجاری‌سازی FrenchReader

وضعیت: **پیشنهاد اولیه — جدا از نقشهٔ راه فنی محصول**

این سند جهت کلی تجاری‌سازی پروژه را ثبت می‌کند. جزئیات آن پس از مشخص‌شدن بازار هدف، قیمت اشتراک، تعداد کاربران و نتایج آزمون مدل‌ها بازبینی می‌شود. این برنامه عمداً وارد `ROADMAP.md` نشده است.

## مدل محصول

- قابلیت‌های اصلی خواندن، کتابخانه و ابزارهای پایه بدون وابستگی اجباری به سرویس ابری باقی بمانند.
- قابلیت‌های پرهزینهٔ هوش مصنوعی به‌صورت اشتراکی یا با سهمیهٔ ماهانه ارائه شوند.
- حالت رایگان می‌تواند شامل تعداد محدودی درخواست ابری و قابلیت‌های آفلاین باشد.
- سطح Premium می‌تواند توضیح گرامر، خلاصه‌سازی، ساده‌سازی CEFR، تولید سؤال و فلش‌کارت را با سهمیهٔ بیشتر ارائه کند.

## معماری پیشنهادی

اپ Android مستقیماً به ارائه‌دهندهٔ مدل متصل نشود. همهٔ درخواست‌های ابری از backend متعلق به محصول عبور کنند:

```text
Android App
    ↓ HTTPS
Product Backend
    ├── Authentication / Subscription / Quota
    ├── AI Router
    ├── Cache and Usage Metering
    ├── LanguageTool
    └── AI Providers
          ├── مدل ارزان برای کارهای ساده
          ├── مدل متعادل برای کارهای معمول
          └── مدل بزرگ برای درخواست‌های پیچیده
```

backend مسئول نگه‌داری API key، احراز هویت، rate limit، ثبت مصرف، کنترل هزینه، cache، سیاست نگه‌داری داده و تعویض ارائه‌دهنده خواهد بود. کلید ارائه‌دهنده نباید داخل APK قرار بگیرد.

## راهبرد انتخاب مدل

در نسخهٔ اولیه، اجرای مدل بزرگ روی GPU اختصاصی توصیه نمی‌شود. محصول ابتدا از APIهای پرداخت بر اساس مصرف استفاده می‌کند تا کیفیت، هزینه و الگوی واقعی استفاده مشخص شود.

- درخواست‌های ساختاریافته و ساده مانند استخراج واژه یا JSON با مدل ارزان اجرا شوند.
- خلاصه‌سازی و ساده‌سازی معمولی با مدل متعادل انجام شوند.
- مدل بزرگی مانند Qwen3.8 Max فقط برای درخواست‌های پیچیده یا سطح Premium استفاده شود.
- LanguageTool برای غلط‌یابی قاعده‌محور و کاهش وابستگی به پاسخ احتمالی LLM به کار رود.
- یک interface مستقل برای ارائه‌دهندگان تعریف شود تا محصول به یک شرکت یا مدل خاص قفل نشود.

مدل‌های متن‌باز Qwen معمولاً نیاز به خرید وزن ندارند، اما self-host کردن آن‌ها هزینهٔ GPU، مانیتورینگ، مقیاس‌دهی و عملیات دارد. مدل‌های اختصاصی مانند Qwen3.8 Max از طریق API و بر اساس توکن مصرفی پرداخت می‌شوند.

## کنترل هزینه

- طول ورودی، context و خروجی هر قابلیت محدود شود.
- فقط chunk یا پاراگراف مرتبط ارسال شود، نه کل مقاله در هر درخواست.
- پاسخ درخواست‌های تکراری و محتوای عمومی cache شود.
- Thinking فقط برای درخواست‌های پیچیده فعال شود.
- برای هر کاربر سهمیه و سقف هزینهٔ روزانه/ماهانه وجود داشته باشد.
- مصرف ورودی، خروجی، latency، خطا و هزینه به تفکیک قابلیت و مدل ثبت شود.
- مدل بزرگ فقط زمانی فراخوانی شود که مدل ارزان‌تر کیفیت لازم را تأمین نمی‌کند.

## حریم خصوصی و اعتماد کاربر

- پیش از ارسال، به کاربر اعلام شود که متن برای پردازش ابری فرستاده می‌شود.
- دادهٔ حساس تا حد ممکن حذف یا ناشناس‌سازی شود.
- مدت نگه‌داری متن و logها حداقلی و شفاف باشد.
- امکان حذف داده و غیرفعال‌کردن قابلیت‌های ابری فراهم شود.
- منطقهٔ پردازش، قرارداد پردازش داده و الزامات GDPR پیش از عرضه در اروپا بررسی شوند.
- قابلیت‌های پایه بدون ارسال متن به cloud قابل استفاده باقی بمانند.

## معیار مهاجرت به self-host

اجرای مدل متن‌باز روی زیرساخت اختصاصی فقط زمانی بررسی شود که:

- هزینهٔ API طی چند ماه پایدار و بیشتر از هزینهٔ کامل GPU و عملیات شده باشد؛
- تعداد و الگوی درخواست‌ها قابل پیش‌بینی باشد؛
- محدودیت حریم خصوصی یا قراردادی مانع استفاده از API خارجی شود؛
- مدل منتخب در آزمون‌های فرانسوی پروژه کیفیت کافی نشان دهد؛
- تیم توان نگه‌داری inference server، مانیتورینگ، امنیت و ظرفیت پشتیبان را داشته باشد.

تصمیم self-host باید بر اساس هزینهٔ کل مالکیت گرفته شود، نه فقط قیمت GPU. زمان مهندسی، ظرفیت بلااستفاده، redundancy، پشتیبان‌گیری و پاسخ‌گویی به خطا نیز جزو هزینه‌اند.

## مراحل پیشنهادی عرضه

1. **اعتبارسنجی کیفیت:** مقایسهٔ چند مدل روی promptها و rubric فرانسوی موجود در پروژه.
2. **MVP ابری:** ساخت backend ساده با احراز هویت، سهمیه، AI Router و یک ارائه‌دهندهٔ API.
3. **اندازه‌گیری:** ثبت کیفیت، latency، تعداد توکن، هزینهٔ هر قابلیت و نرخ استفادهٔ کاربران.
4. **درآمدزایی:** تعریف سطح رایگان محدود و اشتراک Premium با سقف مصرف مشخص.
5. **بهینه‌سازی:** اضافه‌کردن cache، مسیریابی بین مدل ارزان و بزرگ و کنترل context.
6. **ارزیابی self-host:** مقایسهٔ هزینه و کیفیت مدل متن‌باز با API، فقط پس از رسیدن به مصرف پایدار.

## تصمیم فعلی

- داشتن backend برای نسخهٔ تجاری ضروری است.
- backend اولیه به GPU اختصاصی نیاز ندارد.
- MVP از API مدل استفاده می‌کند و مدل بزرگ فقط برای درخواست‌های ارزشمند و پیچیده فراخوانی می‌شود.
- معماری باید از ابتدا امکان تعویض provider و اضافه‌کردن self-host در آینده را داشته باشد.
- جزئیات اجرایی این برنامه فعلاً به `ROADMAP.md` منتقل نمی‌شوند.
